# Solution 中文文案架构设计

## 目标

先建立 20 个 Solution 详情页的中文母稿，解决现有页面标题、关系说明、服务板块和应用场景高度模板化的问题。中文确认后，再按语义分别创作英文与波斯文，不进行逐字翻译。

## 已确认的结构基准

所有页面严格沿用现有 Cisco 详情页，不重新设计信息架构：

1. `01` 首屏：分类、Logo、主标题、绿色标题、短介绍、两个 CTA、主视觉
2. `02` 合作价值：板块标题、说明、三个理由卡片
3. `03` JOTO 服务：板块标题、说明、三个服务卡片及能力点
4. `04` 代表项目：Cisco 保留三个已确认项目；其余 19 页保留板块位置但暂不展示项目内容，等待 JOTO 资料库提供经确认材料
5. `05` CTA：标题、说明、Contact 按钮

Cisco 页面是本轮实施的不可变基准：标题、介绍、合作价值、服务、CTA 和三个已确认代表项目均不修改。其他 19 个页面使用相同字段与顺序，但内容根据厂商能力独立编写。

## 内容策略

- 每个页面围绕该厂商最具辨识度的业务价值展开，而不是把厂商名替换进统一模板。
- 首屏采用“产品领域主标题 + 客户成果绿色标题”，不使用“由 JOTO 交付”一类供应商视角表达。
- JOTO 的角色放在短介绍、合作价值和服务能力中，以咨询、集成、实施和持续运营来体现。
- 除 Cisco 外，其余 19 页的第 `04` 板块统一命名为“代表项目”并暂时留空。Cisco 保留现有三个已确认项目。后续新增的客户名称、项目范围、时间与成果必须由 JOTO 资料库材料支持，并经过内部确认后才能发布。
- 未经当前资料确认的合作等级不写入正文。JOTO 老官网可验证的 Extreme、KnowBe4、OneLogin 关系只采用克制表述。
- 所有 CONTACT 类 CTA 使用统一目标 `/contact`；本设计不修改 Contact 页面。

## 单页字段规则

- 文案总表中的每个页面必须逐项列出 `01–05`，以便确认后直接映射到 `PartnerDetail` 数据字段。
- `02` 的每个理由必须包含标题和说明，不能只列关键词。
- `03` 必须包含板块标题、板块说明、三张服务卡标题与说明；能力点沿用已验证的产品范围。
- `04` 中 Cisco 保留现有内容；其他 19 页只保留“代表项目”板块定义，不预写案例或场景，也不在公开页面展示内部等待说明。
- `05` 必须包含标题、说明，并记录统一 `/contact` 路由。

## 文风

- 中文先写，句子自然、简洁、面向企业决策者和 IT 负责人。
- 避免空泛词：领先、赋能、全栈、卓越、颠覆，除非后文能说明具体价值。
- 避免把产品功能列表当作价值主张；优先说明客户获得的可见性、效率、安全性、可靠性或运营简化。
- 产品名只采用厂商官方公开使用的名称，并避免写入容易过时的具体版本号。

## 并行工作边界

- 中文母稿已经用户确认，本轮在隔离分支中将其按语义适配为当前英文页面内容。
- 本轮只修改 Solution 详情页集中内容数据、空代表项目的必要渲染逻辑及其测试；不修改首页、Contact 页面、导航结构或其他已完成页面。
- 中文与波斯文由并行语言任务继续处理；合并时按 `PartnerDetail` 字段映射，不覆盖本轮已确认的厂商差异化结构。

## 验收方式

- 逐页检查主标题、绿色标题、首屏介绍和各板块是否能脱离厂商名仍体现不同定位。
- 检查 Cisco 数据对象与实施前基线完全一致。
- 检查其他 19 个页面不存在统一的“由 JOTO 交付”句式。
- 检查各厂商产品与服务范围符合其公开产品领域。
- 检查其他 19 页不显示场景或未核实代表项目，Cisco 仍显示三个已确认项目。
- 检查所有事实性产品定位均可追溯至官方厂商资料或 JOTO 老官网；厂商官网只能证明产品能力，不能证明 JOTO 合作等级或既往交付。
- 对没有公开 JOTO 关系证据的厂商，只描述拟提供的服务范围，不写合作等级、认证、客户或既往成果，并在发布前交由内部 Solution Owner 确认。
