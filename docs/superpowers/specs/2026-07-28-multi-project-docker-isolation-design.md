# 多项目 Docker 运行环境隔离设计

日期：2026-07-28
状态：已由用户确认

## 背景

`9. Vibe Coding` 目录下同时存在 Node.js、Python、Swift/Xcode、PostgreSQL、
SearXNG 和静态资料项目。部分项目已经在本机生成 `node_modules`、`.venv`、
构建缓存或独立 Compose 配置。不同项目依赖的语言版本和服务端口并不一致，
继续共用本机运行环境会增加版本冲突、端口冲突和误用依赖的风险。

本设计采用“每个项目独立 Docker Compose”的方式隔离开发环境。源码继续保留
在当前目录，不把项目文件存入 Docker，也不批量搬动目录。

## 目标

- 每个可运行项目拥有独立的语言版本、依赖、网络、数据卷和端口。
- 项目能够使用统一形式的命令独立启动、停止、构建和验证。
- 多个项目同时运行时不发生端口、网络、依赖或持久化数据冲突。
- Node.js 和 Python 项目不依赖 Mac 上的全局包或全局语言环境。
- Swift/Xcode 原生应用继续在 Mac 上运行，其后端和基础服务由 Docker 隔离。
- 现有本机依赖先保留，只有在对应 Docker 环境验证成功后才单独清理。
- 所有密钥只在运行时注入，不进入镜像、Compose 文件或 Git。

## 非目标

- 不把纯资料目录强行容器化。
- 不在本轮重新设计业务代码或升级主要依赖。
- 不建立一个同时控制所有项目的超级 Compose。
- 不在 Docker 中构建或运行依赖 macOS SDK 的 Swift/Xcode 图形应用。
- 不自动删除 Docker 数据卷、本机依赖或用户未提交的文件。
- 不要求所有项目同时常驻运行。

## 方案选择

采用每项目独立 Compose：

- 每个项目自行保存 Docker 配置和运行说明，可独立复制、验证和回滚。
- 项目之间没有共享网络、共享依赖卷或共享数据库。
- 原生应用采用“Xcode 本机界面 + Docker 后端服务”的混合模式。

未采用以下方案：

- 总 Compose：统一入口会重新产生跨项目耦合。
- 本机版本管理器加部分容器：Node.js/Python 依赖仍可能污染本机并互相影响。

## 每项目文件结构

根据项目实际技术栈，在各自仓库或项目目录中添加：

- `Dockerfile` 或按服务拆分的具名 Dockerfile。
- `compose.yaml`，作为该项目唯一的开发环境入口。
- `.dockerignore`，排除 `.git`、本机依赖、缓存、构建产物和密钥文件。
- `.env.example`，只记录非敏感变量名和安全示例值。
- Docker 使用说明，记录构建、启动、停止、测试、端口和常见故障。

已有 Compose 的项目在原配置上扩展，不直接用模板覆盖。总目录另建项目清单，
按“Web 应用、原生混合应用、纯资料”分类，记录每个项目的目录、端口和命令。

## 依赖与运行规则

### Node.js

- 使用项目现有 lockfile 和对应的确定性安装命令。
- Node.js 基础镜像固定明确版本，不使用浮动的 `latest`。
- 源码可挂载进开发容器，但 `node_modules` 使用项目专属命名卷或镜像层。
- 开发服务器在容器内监听 `0.0.0.0`，只通过 Compose 映射到
  Mac 的 `127.0.0.1`。
- 缺少 lockfile 时先补齐锁定机制，不静默升级主要依赖。

### Python

- 依照各自 `pyproject.toml` 固定 Python 版本。
- Python 3.12 项目使用 3.12 镜像；`AI 解读` Worker 按声明使用
  Python 3.14。
- 虚拟环境和包安装在镜像或项目专属卷中，不复用本机 `.venv`。
- 依赖缺少完整锁定时，先记录现状并采用可重复安装方式，不借机升级业务依赖。

### 数据库与基础服务

- PostgreSQL、SearXNG 等服务只加入所在项目的默认 Compose 网络。
- 服务间使用 Compose 服务名通信，不使用容器内的 `localhost`。
- 有状态数据使用项目专属命名卷。
- 数据库默认不暴露到 Mac；只有确有调试需求时才使用固定的
  `127.0.0.1` 高位端口。
- Compose 项目名、网络和卷均带项目唯一前缀。

### Apple 芯片

- 优先使用官方、多架构且原生支持 `arm64` 的镜像。
- 只有上游组件没有 Apple 芯片镜像时才允许使用 x86 模拟，并在项目说明中记录。

## 配置与密钥

- 不读取或复制现有 `.env` 的敏感值到镜像和 Git。
- `.env.example` 仅提供变量名、安全默认值和用途说明。
- Compose 使用 `env_file` 或显式环境变量在运行时注入配置。
- 前端只能获得明确允许公开的变量。
- 镜像构建上下文排除 `.env`、证书、令牌、本机绝对路径和私有数据。

## Git 与现有工作保护

- 实施前记录每个 Git 仓库的分支和工作区状态。
- 不修改、暂存或提交用户已有的未提交文件。
- 每个仓库的 Docker 配置独立验证、独立暂存、独立提交。
- 无 Git 的项目只添加配置文件，不擅自初始化仓库。
- 当前本机的 `node_modules`、`.venv` 和缓存先保留。
- 清理本机依赖是验证后的独立步骤，每个目标均需重新确认。

## 实施顺序

1. 启动并检查 Docker Desktop，记录全部项目基线状态。
2. 处理 `Workbuddy 假网站` 和 `Marketing/Brochure`，验证基础 Node.js
   容器模式。
3. 处理 `JOTO Sunny Try` 和 `JOTO Cisco Solution - Persian` 的多服务
   Web 环境。
4. 处理带 PostgreSQL 的 `SalesFlow`。
5. 处理 `AI 解读`、`JargonLens` 和
   `销售电话和话术沟通智能助手` 的原生/后端混合环境。
6. 更新总项目清单并执行跨项目并行启动验证。
7. 在所有相关验证通过后，逐项目决定是否清理旧本机依赖。

前一个项目验证失败不会阻止对独立项目的只读分析，但在确认失败原因前不将同一
未验证模板批量复制到后续项目。

## 范围拆分与检查点

本文是跨项目的总设计标准，不把所有仓库合并成一个不可分割的实施任务。实际
执行拆成以下五批，每批具有独立实施计划、验证记录和 Git 提交：

1. Docker 基线、`Workbuddy 假网站`、`Marketing/Brochure`。
2. `JOTO Sunny Try`。
3. `JOTO Cisco Solution - Persian`。
4. `SalesFlow`。
5. `AI 解读`、`JargonLens`、`销售电话和话术沟通智能助手`，其中每个原生
   项目仍分别构建和验证。

每批完成后检查通用模板是否需要调整，再开始下一批。后续批次可以复用已经
验证的模式，但不得通过跨项目共享网络、数据卷或依赖目录来减少配置文件数量。
第一份详细实施计划只覆盖第 1 批；其余批次在前一批验证结论明确后分别制定，
避免把尚未验证的假设扩散到全部仓库。

## 验证策略

每个项目必须完成与其能力相匹配的验证：

1. 从干净构建缓存条件下完成镜像构建。
2. Compose 服务启动且健康检查通过。
3. 浏览器、HTTP API、WebSocket 或后台任务能够通过约定方式访问。
4. 项目已有的测试和构建命令在容器环境中通过。
5. `docker compose down` 后重新启动，验证预期数据是否保留。
6. 与至少一个其他项目同时运行，确认没有端口、网络和依赖冲突。
7. 原生混合项目验证 Xcode 应用能够连接到容器化后端。

对于没有 HTTP 服务的构建工具项目，以构建产物、测试结果和输出文件权限作为
主要验证依据。

## 故障处理

- 保留完整构建和服务日志，先定位镜像、依赖、网络、权限或业务测试问题。
- 不通过升级主要依赖、删除数据卷或改写业务逻辑来掩盖容器化问题。
- 容器内文件归属应与宿主使用场景兼容，避免生成无法由当前用户修改的产物。
- 已有端口约定优先保留；发生冲突时只调整 Compose 的宿主端口和对应文档，
  尽量不改业务内部端口。
- Docker Desktop 资源不足时只启动当前项目，并根据实测记录最低资源建议。

## 停止与回滚

- 正常停止使用 `docker compose down`，默认保留命名卷。
- 不自动执行 `docker compose down -v`。
- Docker 配置可通过各项目的独立 Git 提交回滚。
- 在 Docker 验证完成前保留原本的本机依赖和启动方式。
- 单个项目失败时只回滚该项目，不影响其他项目或总清单。

## 验收标准

- 任意 Web、Python 或后端项目都能在只安装 Docker Desktop 的 Mac 上，
  按项目说明独立构建并启动。
- 原生项目除 Docker Desktop 外只依赖 Xcode 和项目声明的 macOS 权限。
- 所有对外开发端口固定绑定到 `127.0.0.1`，且端口表中没有冲突。
- 多个项目能够同时运行，不共享依赖目录、默认网络或持久化数据。
- 敏感配置不出现在镜像层、Compose 文件、示例环境文件或 Git 提交中。
- 每个项目具有明确的启动、停止、测试、日志和回滚说明。
- 现有未提交工作和本机依赖在整个迁移验证期间保持可恢复。
